# Баланс (Balan$)

Telegram-бот для личного учёта: текст, голос, фото чека, скриншот или PDF → операция → баланс и отчёт. Python 3.12+, aiogram и PostgreSQL. Бот не подключается к банковским счетам.

Актуальное [ТЗ для сдачи проекта](docs/01-first-version.md), [аудит и статусы исправлений](docs/27-project-ux-audit.md), [модель БД](docs/03-database-design.md). Документы отдельных этапов описывают историю разработки; текущий публичный интерфейс — личный учёт с одним балансом.

## Текущий пользовательский сценарий

- По умолчанию распознанная операция сохраняется автоматически. Неясная сумма, валюта, тип операции или вероятный дубль требуют уточнения; явный отказ платежа не записывается как расход. Режим подтверждения можно включить в настройках.
- В карточке результата только «✏️ Изменить». При открытии редактора показываются только «Изменить сумму», «Изменить дату», «Изменить описание», «Изменить категорию» и «Отмена».
- После нажатия кнопки изменения отправленное новое значение сохраняется автоматически: временные сообщения редактора удаляются, а исходная карточка операции редактируется на месте и сохраняет кнопку «✏️ Изменить». Отдельного подтверждения сохранения нет.
- Отрицательный начальный остаток показан с минусом. Повторный вход открывает имеющуюся запись.
- У файла без корректной даты, в том числе ошибочно распознанной будущей, используется дата отправки в часовом поясе пользователя и обычный 📅. Будущие операции не поддерживаются.
- Проверка вероятных дублей между источниками предлагает отдельную операцию либо прикрепление к существующей; одинаковый текст не запрещает реальные повторные покупки.
- В автоматическом режиме строки одной покупки с одинаковой категорией, датой, валютой и счётом объединяются в один расход; разные категории сохраняются отдельными операциями. Разбиение полного чека по категориям доступно в режиме подтверждения списка операций. Редактор сохранённой операции остаётся ограниченным четырьмя полями и отменой.
- История: типы операций, по 5 записей, поиск и редактирование. Отчёт: PDF, детализированный PDF, CSV, ИИ-анализ, время снимка и обновление.
- Настройки: валюта до начала истории, часовой пояс, категории, приватность, рабочие переключатели распознавания и уведомлений, очистка истории и отдельное удаление профиля.
- Недоступные реальные дополнения подписки не предлагаются к покупке. Их тестовые сценарии доступны только разрешённым демоаккаунтам.
- Основное взаимодействие — кнопки; в Telegram опубликована команда `/start`. Старые команды счетов и общих бюджетов заблокированы на публичном входе; для ранее выбранного общего бюджета есть возврат в личный без удаления данных.

## Запуск в текущем рабочем каталоге

Проверьте наличие собственного `.venv`, PostgreSQL и локального `.env`. Не копируйте секреты в переписку или Git. Для новой среды используйте раздел подготовки ниже. После переноса проекта виртуальное окружение лучше пересоздать: пути в исполняемых файлах могут ссылаться на прежний каталог.

1. Создайте бота командой `/newbot` у [@BotFather](https://t.me/BotFather), если его ещё нет. [Инструкция Telegram](https://core.telegram.org/bots/tutorial#obtain-your-bot-token).
2. Откройте локальный `.env` в редакторе и заполните `BOT_TOKEN=...`. При желании укажите `SUPPORT_CONTACT=@ваш_username`.
3. Из корня проекта выполните:

```bash
.venv/bin/python -m balans
```

Откройте бота в Telegram и отправьте `/start`. При запуске приложение проверяет runtime-права БД, вызывает `getMe` и устанавливает список команд. Работает один polling-процесс; остановка — Ctrl+C. Если уже установлен webhook, приложение завершится с объяснением и не удалит его автоматически.

Наличие инструкции не означает, что локальный бот сейчас запущен. Серверное развёртывание описано отдельно; не запускайте второй экземпляр для рабочего токена. Исторический этап: [AI-категоризация](docs/05-stage-3.md).

## Установка с нуля

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
```

Запустите локальный PostgreSQL. При доступе администратора БД:

```bash
.venv/bin/python scripts/dev_setup.py
```

По умолчанию используется `dbname=postgres host=localhost` под текущим системным пользователем. Для другого сервера задайте `POSTGRES_ADMIN_DSN` через окружение. Скрипт создаёт БД и две отдельные роли с уникальными именами и случайными паролями; существующий `.env` не перезаписывает. Он не устанавливает PostgreSQL и не меняет существующие БД. Административная учётная запись применяется только для provisioning; приложение получает ограниченную runtime-роль.

Для управляемой БД подготовьте отдельного владельца схемы и runtime-роль без `SUPERUSER`, `BYPASSRLS`, членства в роли владельца или права смены на неё. Владелец должен иметь право создавать схему и таблицу миграций в `public`. Заполните `.env` по `.env.example` и выполните:

```bash
.venv/bin/python -m balans.migrate
```

Runtime-роль по умолчанию берётся из `DATABASE_URL`; её можно явно задать через `--runtime-role`. Миграции выполняются отдельной строкой `MIGRATION_DATABASE_URL`. Бот её не использует. Применение атомарное, с блокировкой и контрольной суммой; повтор допустим, изменение уже применённого SQL отвергается. Новые изменения оформляйте следующей миграцией. Для резервирования данных используйте штатный `pg_dump` с подходящей резервной ролью; проверяйте восстановление до рабочего использования.

## Учёт и надёжность

`users → workspaces → memberships/accounts/categories → operation_drafts → operations/operation_revisions → journal_entries/postings`. Каждая финансовая сущность привязана к пространству, составные FK исключают ссылки на чужие категории и счета. Доступ к данным ограничен PostgreSQL RLS; runtime не имеет прав прямого изменения журнала. `save_expense()` создаёт операцию, версию, проводку и аудит в одной транзакции. Отложенный триггер проверяет соответствие суммы, счёта, даты и проводки.

Суммы — Python `Decimal` и PostgreSQL `numeric(20,6)`, ручной ввод RUB ограничен двумя знаками после запятой; неоднозначные/некорректные суммы не округляются молча. «Сегодня/вчера» относятся к дате начала ввода в сохранённом часовом поясе; бот показывает эту дату при запросе. Новая настройка зоны не меняет уже открытый черновик.

Черновики живут 24 часа, переживают перезапуск, истёкшие отменяются при следующем обращении пользователя. Сохранённые данные не отменяются командой `/cancel`.

Для событий операций ответ сохраняется вместе с изменением состояния. Повтор использует тот же ответ; блокировка пользователя и уникальный источник операции защищают от конкурентного сохранения. Polling сначала сохраняет события во входящую очередь, затем сдвигает offset; обработка выполняется отдельными обработчиками. Сбой после успешной доставки может дать повтор сообщения, но не вторую операцию. Транзакции и соединения используют контекстные менеджеры psycopg.

## Проверка

```bash
.venv/bin/pytest -q
```

Тесты создают отдельную временную БД и две роли через `POSTGRES_ADMIN_DSN`, затем удаляют только их. Нужен работающий PostgreSQL и административные права для создания тестовой БД/ролей. SQLite или имитация БД не используются.

Локальная проверка 15.09.2026: **350 passed**, два предупреждения pypdf. Дополнительно проверены очистка исходной карточки и всех временных сообщений редактора в Telegram, точный состав кнопок до и после изменения и повторное сохранение. Проверяются: суммы и даты, регистрация, ручной расход, история/отчёт/остаток, перезапуск, отмена/срок черновика, повтор update, параллельные подтверждения, RLS, подмена категории/кнопки, запрет прямого изменения проводок, старые кнопки после исправления, повтор миграций, приватность Telegram-чата и повтор после сбоя отправки. Для AI дополнительно проверены реальный SDK через тестовый HTTP-транспорт, ошибки/таймауты/отказы, некорректный JSON и чужие ID, отсутствие повторных API-вызовов, поздние результаты после отмены, исправления и приватность правил.

## Границы этапа

В коде сохранены модули этапов 2–18: личный и совместный учёт, счета и проводки, выдачи и сверка, исправления с аудитом, документы и закрытые периоды, текст/голос/изображения, отчёты и передаваемые копии, лимиты и уведомления. Это перечень серверных модулей, а не меню текущей личной версии. Подробные проверки: [журнал выполнения](docs/implementation-progress.md).

Подписка Stars, квоты, панель с TOTP, приватность, валюты, защищённый webhook, очередь и резервирование реализованы. Для включения оплаты и панели требуются настройки владельца, цены, квот, TOTP и политики. В проекте настроено серверное развёртывание. Реальные платежи, актуальные настройки сервера и внешние резервные копии не проверяются обычными регрессионными тестами. См. [запуск и восстановление](docs/20-stage-18.md).

`/budget` — месячные лимиты; `/budgetday` — начало периода; `/notify` — настройки уведомлений (доставка выключена по умолчанию). Общие пространства: `/workspaces`, `/workspace`, `/members`; выдачи: `/funds`; документы и проверки: `/docs`, `/reviewqueue`. Описание каждого этапа находится в `docs/`.

## Настройка AI

В локальном `.env` предусмотрены:

```dotenv
OPENAI_API_KEY=
OPENAI_MODEL=gpt-4.1-mini-2025-04-14
AI_TIMEOUT_SECONDS=10
AI_CONFIDENCE_THRESHOLD=0.75
```

`OPENAI_API_KEY` — отдельный ключ OpenAI API, не Telegram-токен. Ключ уже добавлен владельцем: реальный запрос категоризации и OCR на синтетических фото/PDF проверены. После добавления ключа перезапустите единственный процесс `.venv/bin/python -m balans`, в Telegram откройте `/ai` и включите AI. Правила и ручной выбор работают без ключа.

Проверка API без отправки пользовательских расходов:

```bash
.venv/bin/python scripts/check_ai.py
.venv/bin/python scripts/check_ai.py --eval
```

Первая команда отправляет один синтетический пример, вторая — десять. Это реальные API-запросы, отдельные от обычных тестов. При отсутствии ключа команды завершаются без вызовов API. Полный контракт, промпт, правила обучения и ограничения — в [описании этапа 3](docs/05-stage-3.md).


## Чеки: этап 4

1. Обработка чеков включена по умолчанию. `/receipts` показывает текущий набор и подсказку.
2. Отправьте фотографию или PDF/JPEG/PNG. Результат появится автоматически. Страницы многостраничного чека отправляйте одним Telegram-альбомом. Разные покупки отправляйте по отдельности.
3. В автоматическом режиме покупка с распознанной суммой сохраняется сразу, без подтверждения оплаты; карточка содержит только **«✏️ Изменить»**. Статусы pending/unknown не блокируют запись, а явный failed и существенные неоднозначности остаются на проверке. В режиме подтверждения доступны прежние шаги проверки и кнопка **«Сохранить расход»**.

Лимиты: 15 МБ на файл, 10 страниц и 30 МБ на набор, до 100 распознанных позиций. Поддерживаются RUB, USD и EUR, но валюта чека должна совпадать с валютой выбранного счёта. PDF с паролем не обрабатывается. PDF-текст извлекается локально, все страницы рендерятся и вместе с текстом передаются модели; фото и сканы читаются через vision OCR. При неуверенном итоге бот просит ручное уточнение. Если дата не распознана, некорректна или ошибочно находится в будущем, используется дата отправки файла в часовом поясе пользователя и показывается обычный значок даты; её можно исправить кнопкой «Дата». Сумма внесённых денег и сдача не должны заменять итог; повторные расходы требуют отдельного подтверждения.

Оригиналы сохраняются в `.local/receipts` (каталог 700, файлы 600), исключены из Git. Можно изменить путь через `RECEIPT_STORAGE_DIR`. Срок хранения исходников — 90 дней; работающий бот очищает истёкшие файлы при запуске и затем раз в час. После истечения срока выдача оригинала блокируется, операция и распознанные позиции остаются. При выключенном боте физическая очистка произойдёт после следующего запуска. Для резервной копии нужны и БД, и каталог оригиналов.

Для обновления существующей установки: остановите polling-процесс, установите зависимости из `requirements.lock`, выполните `.venv/bin/python -m balans.migrate`, затем запустите `.venv/bin/python -m balans`. Набор миграций текущей версии находится в каталоге `migrations/`; отдельные записи о локальном перезапуске не являются частью инструкции.

Дополнительная реальная проверка OCR на трёх синтетических чеках:

```bash
.venv/bin/python scripts/check_receipt_ai.py
```

Команда делает три OpenAI API-запроса. Фото, текстовый PDF и PDF-скан проверены: итог 150 ₽, две позиции; внесённые 200 ₽ и сдача 50 ₽ не попали в сумму расхода. Это небольшая smoke-проверка, а не гарантия точности на всех чеках.

Подробности и границы: [этап 4](docs/06-stage-4.md).

## Голосовой ввод

Запишите и отправьте голосом один расход: «Вчера потратил 850 рублей на продукты». В автоматическом режиме проверьте сохранённую карточку и при необходимости нажмите «Изменить»; в режиме подтверждения нажмите «Сохранить». Используется существующий `OPENAI_API_KEY`; дополнительный ключ не нужен. Подробности и ограничения: [этап 5](docs/07-stage-5.md).

## Отчётность

- `/report` — текущий месяц; `/report сегодня`, `/report вчера`, `/report неделя`, `/report 2026-08` или `/report 01.09.2026 10.09.2026`.
- `/pdf [период]` — PDF с графиками категорий, динамикой и крупнейшими расходами.
- `/analyze [период]` — AI-анализ после подтверждения передачи сводных данных.
- `/csv [период]` — полный список выбранных операций, пригодный для импорта в Google Sheets.
- Google Sheets отключён в текущем интерфейсе; CSV можно импортировать самостоятельно.

PDF, CSV и анализ используют один снимок данных. В карточке доступны CSV и «Обновить», а также время формирования. Историческое описание интеграции Google и ограничений: [этап 6](docs/08-stage-6.md).

Миграция 019 включает обработку для существующих пользователей, которые ранее не давали отдельного согласия; ранее включённые и затем отключённые каналы остаются выключенными.

Карточки ввода показывают описание или позиции, сумму, категорию и дату, без бюджета, счёта, часового пояса, пояснения об источнике даты и статуса «Пока не сохранён». Голос выдаёт результат без промежуточного сообщения. Изображения распознаются автоматически; страницы Telegram-альбома собираются перед одним запросом. В автоматическом режиме после записи остаётся только «✏️ Изменить», а одинаковые категории одной покупки объединяются. Разбиение доступно в режиме подтверждения и предлагает категории товаров с точными суммами; неполный перечень и расхождение с итогом блокируют разбиение. В отчёты входят подтверждённые операции, исходные документы остаются прикреплёнными.
