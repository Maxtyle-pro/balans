# Этап 3: AI-категоризация и исправления

10 сентября 2026 года. Код и миграция 002 реализованы, миграция применена к локальной БД. Telegram-бот перезапущен. Проверен 51 автоматический тест; реальные вызовы OpenAI пока не выполнены — требуется `OPENAI_API_KEY`.

## Пользовательский сценарий

1. `/ai`: бот описывает передачу описания покупки и списка категорий в OpenAI. Кнопка «Включить AI» включает подбор для пользователя. `/ai off` отключает его; личные правила сохраняются. Версия согласия и время включения хранятся в настройках.
2. `/add 250` → `Капучино в кофейне`. Приоритет: явный выбор категории пользователем → личное правило для точного описания → правило по целым словам → AI.
3. Бот показывает предложенную категорию с кнопками подтверждения и изменения. Дальше спрашивает дату и показывает карточку расхода. Автоподбор категории не сохраняет финансовую операцию автоматически.
4. При ошибке API, отсутствии ключа/согласия, отказе, некорректном ответе или недостаточной уверенности бот предлагает выбрать категорию вручную. Неоднозначные покупки не получают незаметно фиктивную категорию.
5. `/manual` сохраняет прежний ручной сценарий. Все существовавшие до миграции черновики остаются в нём и могут быть завершены.

## Исправления и обучение

До сохранения: «Другая категория» / «Категория» или `/category Название`. После сохранения: «Исправить категорию», либо «Категория №…» в `/history`.

Исправление сохранённой операции создаёт новую `operation_revisions` и запись аудита. Предыдущая версия остаётся, сумма/дата/счёт не меняются, проводки не добавляются. Отчёт группирует расход по новой категории, остаток остаётся прежним. Устаревшая кнопка проверяется по ожидаемой ревизии.

После исправления бот предлагает «Запомнить для меня». Только эта отдельная кнопка создаёт личное сопоставление нормализованного полного описания с категорией. Например, после исправления «Кофе в кофейне» на «Продукты» повтор того же описания предлагает «Продукты» без API-запроса. Регистр, пунктуация, повторные пробелы и ё/е нормализуются. Отмена черновика или последующее изменение категории делает старое предложение обучения недействительным. Если правило уже явно сохранено, оно существует независимо от дальнейшей отмены расхода; отключается через `/rules`.

Для более широких правил есть `/rule такси | Транспорт`. Совпадение по целым словам: «такси до дома» подходит, «таксидермия» — нет. Точное исправленное описание имеет приоритет над правилом по словам; среди совпавших правил по словам выбирается наиболее длинная фраза, затем стабильный порядок ID. Повтор `/rule` с той же фразой обновляет категорию и включает правило. `/rules` выводит по пять правил на страницу с кнопками отключения.

Это обучение через подтверждённую персональную память в БД. Оно не меняет веса модели и не переносит исправления в данные других пользователей. Автоматическое выделение продавца и merchant-правила в этот этап не включены: описание покупки может содержать разные товары одного продавца, поэтому молчаливое обобщение было бы ненадёжным.

## API и промпт

Адаптер: [`balans/ai.py`](../balans/ai.py). Системный промпт: [`category_v1.txt`](../balans/prompts/category_v1.txt), версия `category-v1`. Пользовательская часть запроса строится как JSON из описания и разрешённых категорий. В неё не добавляются сумма, дата, Telegram ID или история. Если сам пользователь написал персональные данные в описании, это описание передаётся как введено.

Используется OpenAI Responses API, `responses.parse`, Pydantic-схема с запретом лишних полей и проверка ID по списку текущего пространства. Результат содержит только `category_id` и `confidence`. `store=False` отключает сохранение ответа для последующего API retrieval; это не обещание отсутствия всех видов хранения у провайдера. Основание формата — [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Модель по умолчанию зафиксирована: `gpt-4.1-mini-2025-04-14`; доступный snapshot указан в [документации модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini). Модель настраивается через `OPENAI_MODEL`; её доступность в конкретном аккаунте подтверждается только реальным API-запросом. Порог уверенности — 0,75; это порог обработки ответа, не измеренная точность классификатора.

Промпт запрещает выполнять инструкции внутри описания и придумывать категории, отличает товары от места покупки, содержит примеры и требует уточнения при недостаточных данных. У модели нет инструментов и доступа к БД. JSON-схема ограничивает форму; содержательный выбор всё равно подтверждает пользователь.

Таймаут SDK — 10 секунд по умолчанию (1–30 в конфигурации), автоматические SDK retries выключены, максимум ответа — 160 токенов. Ошибки сохраняются кодами без сырых ответов и секретов. В `ai_jobs` сохраняются модель, версия промпта, request snapshot, ID ответа, входные/выходные токены и итог. Денежная стоимость и подписочные квоты на этом этапе не рассчитываются.

## Долговечность и изоляция

Миграция [`002_ai_categories.sql`](../migrations/002_ai_categories.sql) добавляет `category_rules`, `category_feedback`, `category_actions`, `ai_jobs`, версию черновика и настройки AI. Новые таблицы защищены RLS по пользователю и workspace, составные FK запрещают привязку категории другого пространства.

Сначала транзакция сохраняет описание, версию черновика и задание с уникальным `(draft_id,draft_version)`. Затем соединение освобождается, выполняется HTTP-запрос и новая транзакция проверяет права, согласие, срок, состояние и версию черновика. Явное исправление или отмена имеют приоритет над поздним AI-ответом. Подтверждённые API-результаты и fallback-ответы сохраняются, повтор update не вызывает API снова.

Задание `running` после аварии не вызывает повторный платный запрос автоматически. Пока действует трёхминутная lease, бот предлагает дождаться или выбрать вручную; после неё при следующем обращении используется ручной fallback. Для осознанной новой попытки можно отменить расход и начать заново. Отдельного фонового worker пока нет: задача выполняется в процессе обработки Telegram update, сохранение состояния позволяет восстановиться после перезапуска. Polling остаётся последовательным; задержка AI может задерживать обработку следующих сообщений. Для масштабирования потребуется отдельный worker/очередь.

## Проверки

`pytest` использует настоящий PostgreSQL и официальный OpenAI SDK с подставным HTTP-транспортом. Проверяются:

- Формат запроса, Structured Outputs, запрет инструментов, отсутствие истории/сумм в payload.
- Валидный ответ, чужой category ID, неполный/некорректный JSON, низкая уверенность, отказ, 401/429/500 и timeout без повторных запросов.
- Новый ввод, сохранение только после подтверждения, fallback и прежний ручной ввод.
- Повтор update и перезапуск без нового вызова AI.
- Отмена, явная категория и отзыв согласия во время запроса без перезаписи поздним результатом.
- Исправления после сохранения: новая ревизия, тот же денежный журнал, обновлённая группировка отчёта.
- Отдельное подтверждение обучения, недействительные/чужие кнопки, RLS и отключение правил.

Для проверки реальной модели добавлены `scripts/check_ai.py` (одна синтетическая покупка) и `--eval` (10 примеров, включая неоднозначные описания и внедрённые инструкции). Они запускаются отдельно и не берут данные пользователей. Пока ключ отсутствует, качество реальной модели не измерено.
