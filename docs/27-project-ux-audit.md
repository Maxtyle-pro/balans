## 1. P1 — Одна покупка из разных источников учитывается дважды

**Воспроизведение.** Включить автосохранение. Отправить «Покупка 150 сегодня», затем скриншот с распознанной покупкой на 150 ₽ той же даты. Получены две операции и баланс −300 ₽. Предупреждения о возможном дубле нет.

**Причина.** Автоматический сценарий проверяет повтор совпадающего набора файлов, а затем ставит `duplicate_confirmed=True`. Проверка похожих операций, существующая в режиме подтверждения, обходится. Идентичный файл и разные изображения одной покупки — разные случаи.

**Правка.** Перед автоматическим сохранением сравнивать реквизиты операции с существующими записями, включая текст и голос. При вероятном совпадении предлагать «Прикрепить к записи» / «Это другая покупка». Не блокировать две реальные покупки только из-за одинаковой суммы.

**Источник:** [automatic_capture.py](../balans/automatic_capture.py), строки 65–84; [media_flow.py](../balans/media_flow.py), `_media_duplicates`.

## 2. P1 — Отрицательный начальный остаток теряет минус в карточке и истории

**Воспроизведение.** «Начальный остаток» → −1000. Карточка: «1 000,00 ₽», история: «1 000,00 ₽», баланс: «−1 000,00 ₽».

**Причина.** Модуль учёта использует `opening_negative`, а компактная карточка и история выводят положительное поле `amount` без этого признака. Баланс считается правильно, но пользователь видит противоречащие суммы.

**Правка.** Общая функция отображения суммы с учётом типа операции и отрицательного начального остатка. Применить её к карточке и истории; в отчётном снимке знак уже учитывается.

**Источник:** [automatic_capture.py](../balans/automatic_capture.py), строки 13–21; [history_ui.py](../balans/history_ui.py), строки 8–14; [shared_reports.py](../balans/shared_reports.py), `_report_snapshot`.

## 3. P1 — Отключение распознавания и уведомлений не исполняется

**Воспроизведение.** После `/voice off` и `/receipts off` значения `voice_enabled` и `receipts_enabled` остаются true. После `/notify off` при предварительно включённых уведомлениях `enabled` и `monthly` тоже остаются true. Вместо изменения настройки приходит общая фраза об автоматической работе.

Есть и обратная проблема: `/ai off` действительно отключает ИИ, но предложенная при следующем вводе кнопка «Настройки ИИ» не включает его и сообщает, что распознавание работает автоматически. Выход — знание скрытой команды `/ai on`.

**Причина.** Упрощённое меню возвращает ответ до вызова обработчиков настроек. Текст приватности при этом обещает возможность отключения.

**Правка.** Сохранить автоматическую работу по умолчанию, но выполнять явно выбранное отключение. Показывать фактическое состояние и работающую кнопку включения. Для уведомлений различать пользовательские сводки и необходимые сервисные сообщения.

**Источник:** [simple_interface.py](../balans/simple_interface.py), строки 47–50; [text_recognition.py](../balans/text_recognition.py), `_text_recognize`; [privacy.py](../balans/privacy.py), `_privacy_command`.

## 4. P1 — Старые команды переключают скрытый бюджет и ломают основной сценарий

**Воспроизведение.** `/workspace Проверка` создаёт общий бюджет и делает его текущим. После этого обычная кнопка «Доход» требует сверки общего прихода. Кнопка `workspaces` возвращает главное меню, но текущий бюджет остаётся общим.

**Последствие.** Интерфейс продолжает выглядеть как личный учёт с одним балансом, однако операции направляются в другое пространство. Действия для работы с ним скрыты; вернуться можно через старую текстовую команду и список бюджетов.

**Правка.** Согласовать доступность старых команд и кнопок. В личном продукте блокировать новые входы в скрытые сценарии. Для пользователей с прежними общими данными дать явный переход в личный бюджет без удаления истории.

**Источник:** [simple_interface.py](../balans/simple_interface.py), `HIDDEN_ACTIONS` и ветка `workspaces`; [workspaces.py](../balans/workspaces.py), строки 19–30.

## 5. P2 — Нет удобного удаления одной записи и исправления ошибочного типа

**Наблюдение.** В автоматически сохранённой карточке есть только «Изменить». В редакторе есть сумма, дата, описание и категория, но нет удаления отдельной операции или смены расхода на доход. Серверная отмена через `fdelete` реализована, однако её кнопку интерфейс не создаёт. В настройках при этом есть удаление всей истории.

Схожая проблема у вложений: к автоматически сохранённой текстовой операции нельзя удобно прикрепить подтверждение через её редактор. Отправка чека отдельным сообщением может попасть в сценарий нового расхода из пункта 1.

**Правка.** Сохранить компактную карточку, а внутри «Изменить» добавить действия «Тип операции», «Прикрепить чек», «Удалить запись». Удаление одной записи подтверждать отдельно и проводить через существующий механизм отмены с аудитом. Смену типа реализовать с корректировкой журнала, не прямым изменением проводок.

**Текущее решение пользователя.** Предложение выше относится к исходному аудиту и не является текущим интерфейсом: редактор показывает только четыре поля («Изменить сумму», «Изменить дату», «Изменить описание», «Изменить категорию») и «Отмена». Системные callbacks расширенных сценариев сохранены только для совместимости старых сообщений и не выводятся в новых кнопках.

**Источник:** [automatic_capture.py](../balans/automatic_capture.py), строка 21; [finance.py](../balans/finance.py), `_finance_prompt`, `_finance_callback`; [documents.py](../balans/documents.py).

## 6. Закрыто решением пользователя — дата файла

**Воспроизведение.** Передать распознанную оплаченную операцию с датой 15.09.2026 при отправке 14.09.2026. Сохраняется 14.09.2026, карточка показывает обычный 📅, предупреждений нет.

**Причина.** Будущая дата сначала обнуляется, затем попадает под новое правило для отсутствующей даты.

**Итоговое правило.** Будущих операций в продукте нет. Отсутствующая или ошибочно распознанная будущая дата файла заменяется датой отправки; карточка показывает обычный 📅. Прежнее предложение уточнять дату отклонено пользователем.

**Источник:** [media_flow.py](../balans/media_flow.py), строки 22–31; [receipts.py](../balans/receipts.py), `_finish_receipt`.

## 7. P2 — Предлагаются покупки, недоступные обычному пользователю

**Наблюдение и проверка.** Экран исчерпанной квоты предлагает «Добавить пакет» и «Выбрать тариф», а экран файлов — «Продлить на 90 дней». Для обычного аккаунта переход заканчивается сообщением: дополнения доступны только для тестирования, реальные цены не утверждены.

**Последствие.** Пользователь воспринимает кнопку как доступное решение проблемы, но не может завершить покупку. Для файлов это особенно неудобно рядом с предупреждением об удалении.

**Правка.** До запуска реальных дополнений показывать доступные варианты: ручной ввод, дату обновления квоты, скачивание файлов и поддержку. Демопокупки оставлять только в тестовом режиме. Реальный платёжный сценарий дополнений — отдельная реализация с проверкой событий оплаты.

**Источник:** [addons.py](../balans/addons.py), `_quota_card`, `_addon_offer` (строка 32), `_retention_card`; [billing.py](../balans/billing.py), `_subscription_card`.

## 8. P2 — «Начальный остаток» предлагает повторное добавление вместо исправления

**Воспроизведение.** После сохранённого начального остатка снова нажать одноимённую кнопку и ввести сумму. Только после ввода появляется ошибка «Начальный остаток уже задан. Исправьте существующую запись». Созданный черновик остаётся незавершённым.

**Правка.** При входе проверять существующую запись. Если она есть — открыть её редактирование с прежней суммой; если нет — начать добавление. Не запрашивать сумму, которую заведомо нельзя сохранить.

**Источник:** [simple_interface.py](../balans/simple_interface.py), строки 25 и 34; [finance.py](../balans/finance.py), `_finance_new`, `_finance_command`.

## 9. P2 — Экран валюты обещает изменение, которое уже запрещено

**Воспроизведение.** После первой сохранённой операции открыть «Валюта». Экран предлагает выбрать валюту «для новых расходов», но выбор другой заканчивается блокировкой: смена требует пересчёта истории.

**Правка.** До показа выбора проверять наличие истории. При заблокированной смене показывать текущую валюту и причину ограничения. Отдельно проектировать переход на новую валюту, если он действительно нужен; не предлагать очистку истории как стандартный обход.

**Источник:** [currency_flow.py](../balans/currency_flow.py), строки 10–20; [024_user_currency.sql](../migrations/024_user_currency.sql), строки 11–25.

## 10. P2 — Приватность и удаление профиля недоступны из обычных настроек

**Наблюдение.** В меню настроек нет перехода к приватности. Сам экран существует и содержит удаление данных, но обычная навигация к нему не ведёт. Сохраняются `/privacy` и `/delete`, которых нет в опубликованном списке команд.

**Правка.** Добавить один пункт «Данные и приватность»: действующая политика, управление обработкой, удаление профиля. «Очистить историю» и «Удалить профиль» должны оставаться разными действиями с понятными последствиями. Возвращать отдельный большой раздел файлов в меню для этого не требуется.

**Источник:** [simple_interface.py](../balans/simple_interface.py), строки 21–29 и 74–75; [privacy.py](../balans/privacy.py), `_privacy_command`.

## 11. P2 — История плохо различает типы операций

**Наблюдение.** Список называется «Ваши операции», но кнопка и вопрос говорят «Изменить расход». В строке показываются описание, положительная сумма, дата и категория; доход с произвольным описанием может визуально не отличаться от расхода.

**Правка.** Переименовать действие в «Изменить операцию». Для каждой строки показывать тип или однозначный знак/значок: расход, доход, начальный остаток, возврат. Сохранить компактный список и существующую защиту выбора по снимку страницы.

**Источник:** [history_ui.py](../balans/history_ui.py), строки 8–18 и `_history_entry`.

## 12. P2 — Экспорт и поиск существуют, но их трудно обнаружить

**Наблюдение.** В отчёте есть два PDF и ИИ-анализ, но нет CSV. В истории нет поиска. Серверные `/csv all` и поиск по описаниям существуют, однако пользователю предлагается пользоваться кнопками, а в Telegram опубликован только `/start`.

**Правка.** Добавить «CSV» в экран отчёта и «Найти» в историю. Для выгрузки большого объёма объяснять ограничения и давать выбор периода. Не возвращать технические команды в тексты финансовых карточек.

**Источник:** [reports.py](../balans/reports.py), `_report_card`, `_report_command`; [history_ui.py](../balans/history_ui.py), `_history_page`; [command_ui.py](../balans/command_ui.py), действие `search`.

## 13. P2 — Разбиение чека недоступно в основном автоматическом сценарии

**Наблюдение.** Для полного оплаченного чека автосохранение происходит до показа карточки с «Разбить по категориям». После сохранения доступно редактирование общей операции; разбиения в нём нет. Возможность, описанная в старом ТЗ как стандартная, фактически доступна в режиме подтверждения.

**Правка.** Добавить в редактор сохранённого чека действие «Разбить по категориям». Замена общей записи частями должна быть атомарной, сохранять оригинал и проверять точное совпадение сумм. Другой вариант — отдельная явно включаемая настройка обработки многопозиционных чеков.

**Текущее решение пользователя.** Сохранённый редактор не показывает кнопку разбиения; разбиение остаётся в сценарии подтверждения списка операций.

**Источник:** [automatic_capture.py](../balans/automatic_capture.py), `_capture_draft`, `_capture_media_item`; [media_flow.py](../balans/media_flow.py), `_media_card`, `_split_lines`; [finance.py](../balans/finance.py), `_finance_prompt`.

## 14. P2 — Условия квот неверно объясняют многостраничный PDF

**Наблюдение.** В деталях пробного тарифа написано «Страницы PDF считаются отдельно». Действующий триггер считает количество файлов в пакете, а не страниц. Один PDF на несколько страниц расходует одну единицу файловой квоты.

**Правка.** Использовать единое описание: «Один PDF — один файл, до 10 страниц в обрабатываемом наборе». Формировать текст условий из общего определения единиц квоты, чтобы разные экраны не расходились.

**Источник:** [onboarding.py](../balans/onboarding.py), строка 83; [023_retention_addons.sql](../migrations/023_retention_addons.sql), строка 153; [23-retention-addons.md](23-retention-addons.md).

## 15. P3 — Старый отчёт выглядит актуальным после исправления операций

**Наблюдение.** Отчёт хранится как снимок. Если после его создания исправить сумму и скачать PDF по старой кнопке, выгружается прежний снимок. Краткая карточка не объясняет это и не предлагает обновление.

**Правка.** Показать время формирования и кнопку «Обновить отчёт» с тем же периодом. Уже скачанный файл остаётся снимком; новый создаётся по текущим данным.

**Источник:** [reports.py](../balans/reports.py), `_report_card`, `_get_report`, `_resolve_report`; [shared_reports.py](../balans/shared_reports.py), `_report_snapshot`.

## 16. P3 — Документы смешивают первоначальные планы, готовые модули и текущий интерфейс

**Наблюдение.** Старое ТЗ требовало обязательного подтверждения, нескольких счетов, совместного учёта и отдельных отсутствующих кнопок; OCR PDF относило к будущему. В README остаются утверждения о локальной версии без настроенного сервера, доступных старых разделах и отключении медиа командами, которые сейчас перехватываются.

**Выполнено в рамках этой проверки.** [Первоначальное ТЗ](01-first-version.md) переработано для сдачи под версию `a50a529`: текущий интерфейс, автосохранение, PDF, реальные ограничения валют, демонстрационные дополнения, хранение и фактическая архитектура. Известные дефекты явно вынесены в ограничения.

**Предложение.** Сделать актуальное ТЗ источником описания сдаваемого продукта; README синхронизировать с ним. Документы этапов оставить историческими, пометив их даты и статус. Наличие функции в серверном коде не описывать как наличие кнопки для обычного пользователя.

## Порядок работ

1. Исправить дубли, знак отрицательного остатка и явные переключатели настроек; закрыть переходы в скрытый контекст.
2. Добавить доступное исправление ошибочной записи внутри «Изменить»; правило даты сохранить по решению пользователя.
3. Устранить тупики начального остатка, валюты, приватности и недоступных покупок.
4. Улучшить историю, поиск, экспорт и разбиение чека.
5. Согласовать условия квот, актуальность отчётов и остальные документы.

## Почему 330 успешных тестов не выявили эти проблемы

Общая фикстура тестов после проверки миграционного значения переключает значение по умолчанию `automatic_capture` на false ради старых сценариев. Тесты автосохранения включают его отдельно. Многие проверки истории, дублей и разбиения поэтому проверяют подтверждение, а не основной автоматический путь.

Часть UI-тестов проверяет отсутствие команд и состав кнопок, но не достижимость действия от главного меню и не изменение соответствующей настройки в БД. Некоторые тесты вызывают внутренний `fdelete` напрямую, хотя кнопки удаления в интерфейсе нет.

Для исправлений нужны проверки пользовательских цепочек: «войти через меню → выполнить действие → проверить финансовый результат и настройки». Особое внимание — отрицательному остатку, повтору покупки через другой источник, отключению/включению каналов и восстановлению после ошибочного ввода.

Источники: [tests/conftest.py](../tests/conftest.py), [test_simple_interface.py](../tests/test_simple_interface.py), [test_automatic_capture.py](../tests/test_automatic_capture.py).

Программные исправления внесены в рабочую копию по последующему запросу пользователя. Исходная формулировка этого аудита выше сохранена как историческое наблюдение; текущий интерфейс определяется актуальным ТЗ и README.
